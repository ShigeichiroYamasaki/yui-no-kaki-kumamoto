# ADR-0001: 本番系の機能仕様

- 状態: Proposed
- 日付: 2026-07-31
- 更新日: 2026-08-04

## 文脈

国内外から認定NPOへの復興支援を受け付け、登録金融・決済事業者による円転後にNPOから熊本県へ別個の円貨寄附を行い、インフラ復旧の進捗を支援者へ返す必要がある。税制優遇、ふるさと納税、義援金の個人配分は対象外とする。

## 決定

本番系は次の機能境界を持つ。

### P-01 支援受付

- 公式に確認されたネットワークと資産だけを許可する。
- ETHはBase Mainnet、公式JPYCはPolygon PoSのチェーン別受付コントラクトで受領する。
- 受付イベントには支援ID、ウォレット、資産、数量、公開用ハッシュを含める。
- 国、メッセージ、表示名は任意であり、原文をオンチェーンへ保存しない。
- 未確認資産、ゼロ金額、停止中の受付を拒否する。

### P-02 玉垣SBT

- ERC-721とERC-5192の組合せを採用し譲渡を禁止する。
- 支援と同じチェーンでSBTを原子的に発行し、`chainId:sbtContract:tokenId`をglobal IDとして統合表示する。
- `Received / Included / Delivered / Reported / Invalidated`を管理する。
- 集約送金バッチと対象支援IDの対応は、明細そのものではなく検証可能なハッシュまたはMerkle rootとして記録し、SBTの状態遷移を追跡可能にする。
- SBTは金銭的権利、返済請求権、公共事業への決定権を表さない。
- 鍵紛失時の失効・再発行は別途本人確認手順を経て、旧トークンと再発行トークンの対応を監査可能な形で記録する。

### P-03 資金管理

- 初期本番候補では支援成立時に資産を認定NPOへ帰属させ、支援者別残高・交換・振替を提供しない。
- トレジャリーからの送金先を、認定NPOと契約し熊本県災害支援口座へ円貨送金する登録金融・決済事業者の入金先に限定する。
- 管理主体はNPOの組織マルチシグとし、個人または技術受託者の単独EOAを使用しない。
- 送金は一意なバッチIDを持ち、二重実行を拒否する。
- JPYC・ETHの円転は登録事業者に委ね、コントラクト自身は交換しない。
- 運営費は復興支援金と分離する。

### P-04 熊本県受領確認

- 県受領確認書や銀行証憑はオフチェーンで保管する。
- オンチェーンには文書ハッシュ、バッチID、円建て確定額、確認時刻のみを記録する。
- 記録権限は熊本県または正式に委任された報告者に限定する。

### P-05 復興報告

- 事業ID、分野、地域、進捗率、支援金充当額、報告書ハッシュを公開する。
- 個別支援と個別工事の一対一因果関係を表示しない。
- 修正は履歴を残し、新しい報告IDとして追記する。

### P-06 DAO参考投票

- SBT保有アドレスは復興分野に関する非拘束の意見表明を行える。
- 1ウォレットへ各提案100ボイスクレジットを付与し、1〜10票の二乗を消費するクアドラティック・ボーティングとする。
- 支援額やSBT保有数によるクレジット増加は行わない。
- 投票コントラクトは支援金を保有・移動・執行できない。
- 熊本県の予算、調達、工事優先順位を拘束しない。

### P-07 可視化

- 支援ウォレット数、件数、資産別数量、参考評価額、円転確定額、県送金額、残高を分離表示する。
- 本番集計は単一の表にBase ETHとPolygon JPYCをchain別の2行として常時表示し、chain切替や独立カードを必要としない。
- 全chainの玉垣SBTを一つのギャラリーへ統合し、各玉垣にはchain名と`chainId:sbtContract:tokenId` global IDを付ける。
- 玉垣表示は、熊本城を囲む全体俯瞰、100本単位の区画、個別玉垣の3段階とする。支援者はウォレット接続、表示名、通し番号、wallet address、transaction hash、global IDから自分の玉垣へ到達できる。
- 個別玉垣にはglobal IDを含む恒久的な共有URLを付け、全体の中で本人の玉垣を強調する。支援額によって玉垣の大きさや配置上の優劣を変えない。
- 大規模化した本番表示はIndexer APIから区画単位で取得し、遠景をCanvas/WebGLまたは密度表現、近景を個別画像として描画する。ブラウザが全SBT metadataを一括取得する構成を本番要件としない。
- トップページにBaseとPolygonの本番玉垣SBTを統合した俯瞰ブロックを置く。テストネットSBTを混在させず、本番SBT addressが未設定または未発行の場合は0本と受付開始前の状態を明示する。
- 異なる資産額は換算根拠なしに合算せず、chain・asset別数量として表示する。
- 国別集計は本人の任意申告に基づく。
- ネットワークごとに定めた確認ブロック数へ達する前の取引は「確認中」として確定値から除外する。
- 確定集計、確認中集計、最終同期ブロック、最終同期時刻を表示する。
- 集計式は`受領 = 県送金済み + 処理中 + 残高 + 明示手数料`とする。

### P-08 セキュリティと運用

- 緊急停止、役割分離、最小権限、監査ログを実装する。
- 管理権限変更と送金にはタイムロックを導入する。
- 本番前に第三者監査、インシデント対応訓練、鍵復旧訓練を行う。
- 制裁・不正流出アドレス対応は登録事業者および専門サービスと設計する。

## 非機能要件

- 可用性目標、RPO/RTO、SLAは熊本県との協議後に確定する。
- イベントインデクサーは再編成と再同期に耐える。
- 公開APIはレート制限、キャッシュ、監視を備える。
- 重要操作は二者承認と改ざん不能な監査ログを要求する。

## 本番移行ゲート

具体的な認定NPOの理事会承認、熊本県との覚書、熊本県災害支援口座、公式JPYCアドレス、登録金融・決済事業者、会計処理、規約、プライバシー方針、監査完了が揃うまで本番受付を開始しない。ADR-0007とADR-0008の本番移行条件を満たし、Critical/Highリスクが未解決でないことを開始承認の必須資料とする。

## プロトタイプとの境界

現在のHardhat実装とEthereum Sepoliaデモは、本ADRの概念とトランザクションフローを検証するためのプロトタイプであり、本番移行ゲートを満たしたシステムではない。プロトタイプでは単一EOAを初期ロールへ設定できるが、本番では禁止する。画像付きSepoliaデモで同意の上オンチェーンSVGへ表示名・メッセージを埋め込む機能も技術実証に限定し、本番採用にはADR-0005に定める追加判断を必要とする。マルチシグ、タイムロック、確認ブロック分離、SBTと集約送金バッチの検証可能な関連付け、鍵紛失時の失効・再発行は本番開始前の必須実装とする。

## 結果

透明性を確保しつつ、DAOが公共予算を支配する構造を避けられる。一方、本番運用は行政・金融・会計上の合意に依存する。
