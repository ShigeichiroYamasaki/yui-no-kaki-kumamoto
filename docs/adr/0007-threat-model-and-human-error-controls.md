# ADR-0007: 攻撃と操作ミスを同じ安全制御で扱う

- 状態: Proposed
- 日付: 2026-08-03

## 文脈

資金損失や虚偽報告は、外部攻撃だけでなく、誤ったアドレス、chain、桁、権限、Safe閾値、銀行口座、証憑hashなどの人為ミスでも発生する。マルチシグを導入しても、全署名者が同じ偽資料や画面を確認すれば防御にならない。

強化前のプロトタイプには、即時の受領先変更、同一ロールによるpause/unpause、引数ベースのERC-20受領額、任意SBT受領者、投票snapshot未実装、訂正不能な報告があった。本ADRに基づくコード強化後も、組織マルチシグ、管理ロールのtimelock、最大滞留時間、supportId包含の完全検証は本番との差として残る。

## 決定

### 1. 二つの独立性を要求する

重要操作は「複数署名」だけでなく、次の両方を満たす。

- **人の独立性**: 提案者、資料照合者、署名者、実行者、事後照合者を可能な範囲で分離する。
- **情報経路の独立性**: 送付先、asset、chain、銀行指図を、同一メールや同一画面ではなく、契約原本、管理台帳、事業者の別経路連絡、オンチェーン読み取りから照合する。

### 2. 重要度別の変更制御

| 操作 | 要求制御 |
|---|---|
| 緊急pause | 少数の専用鍵で即時可能、理由と時刻を記録 |
| unpause | 原因除去、影響確認、別マルチシグ、timelock |
| 通常batch送金 | 財務マルチシグ、simulation、上限、決済指図hash |
| beneficiary・asset・role変更 | 設定マルチシグ、timelock、公開予告、少額試験 |
| Safe owner・threshold・module変更 | beneficiary変更以上の承認、独立監査 |
| 県受領・復興報告 | 報告マルチシグ、原本hash、取消・後継記録 |

### 3. コントラクトへ拘束する

本番開始前に次をコードで強制し、運用手順だけに依存しない。

- beneficiaryの二段階変更とtimelock
- asset別Vault残高上限、batch上限、日次上限、最大滞留時間
- supportId包含Merkle root、前batch hash、決済指図hash、期限
- ERC-20のtransfer前後balance差分による実受領額
- allowlist登録時のchain、address、codehash、decimals、symbol固定
- pauseとunpauseのrole分離
- SBTの自己受領またはEIP-712受領同意
- 投票開始blockのSBT snapshotとInvalidated除外
- attestationの取消、訂正、後継参照

### 4. 不変条件を継続監視する

最低限、次を自動検査する。

```text
Vault実残高 = 累計実受領量 - 累計オンチェーン送付量 + 強制送付等の調整量
各supportIdは高々一つの有効batchへ含まれる
事業者確定円貨 = 県口座入金 + 開示手数料 + 未処理差額
role・owner・threshold・beneficiary・allowlistは承認済み台帳と一致する
```

不一致時は新規送金を自動停止し、人間が原因を特定するまで再開しない。

### 5. 失敗を前提に回復手順を用意する

- 鍵侵害、誤送金、偽入金先、事業者障害、chain停止、誤attestation、個人情報公開を個別runbook化する。
- 本番鍵を使わないtabletop exerciseとtestnet drillを半年ごとに実施する。
- 事故時は事実、影響範囲、最終正常batch、停止状態、次回更新時刻を公開する。
- オンチェーン誤記は削除できないため、取消・後継記録とUI警告で訂正する。

## 理由

攻撃と人為ミスは、最終的に「誤った主体が、誤った内容を、不可逆に実行する」という同じ形になる。独立照合、最小権限、遅延、上限、simulation、不変条件、停止と回復を共通制御にすることで、原因を問わず被害を抑制できる。

## トレードオフ

承認と送金が遅くなり、署名者、監視、文書管理、訓練の費用が増える。災害時の迅速性とのバランスが必要だが、緊急pauseだけは迅速にし、資金送付やunpauseは速度より正確性を優先する。

## 本番移行条件

- 外部監査でCritical/Highが未解決でない
- 本ADRのコード拘束をテストで検証した
- 全署名者が独立照合を含むtestnet drillを完了した
- 誤chain、誤decimals、重複batch、期限切れquote、誤beneficiaryをsimulationで拒否できる
- 鍵侵害と事業者障害のtabletop exerciseを完了した
- 監視とincident連絡が24時間機能することを確認した

## 結果

強化版プロトタイプは、本ADRのコントラクト制御の一部を実装したが、本番移行条件をすべて満たしていない。外部監査、有限な上限設定、組織マルチシグとtimelock、監視・照合基盤、訓練が完了するまではSepolia上の無価値なデモとしてのみ運用する。
